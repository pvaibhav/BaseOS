# spruceOS on BaseOS 2: H700 compatibility audit

Audit date: 2026-11-01. Research only. No handheld, adb, installation, or executable spruce code was used.

## Finding

Unmodified spruceOS does not run correctly on BaseOS 2. The launcher finds it, but spruce selects a Mali/fbdev graphics stack and PyUI opens the absent `/dev/disp` during construction. Fixing only the launch environment is insufficient. Input discovery, audio ownership, suspend, networking, and shutdown also need a BaseOS 2 branch in spruce.

Keep BaseOS 2's standard Linux interfaces. Put model discovery, KMS SDL selection, and calls to `baseos` behind one spruce capability check, `[ -x /usr/bin/baseos ]`, as specified by [the frontend contract](/Users/pvaibhav/.t3/worktrees/BaseOS/feature-h700-mainline/v2/CONTRACT.md:1). Do not revive BSP ioctls, vendor PMIC attributes, or vendor kernel modules to run this frontend.

The main OS-side work is small: guarantee the card alias and required shell/runtime utilities in the built image, preserve the existing identity files, and complete per-model standard input/LED/rumble support where missing. Most compatibility changes belong in spruce because its current implementation selects explicitly vendor-specific APIs.

Installation uses a BaseOS image on TF1 plus the **full spruce release payload**, extracted at the frontend card's root. The PC [spruceOS Installer](https://github.com/spruceUI/spruceOS-Installer/releases/latest) can prepare the card and download TF1 images. Its small installer payload alone is not the runtime BaseOS launches. BaseOS also supports the frontend on TF1's data partition, so integration must handle both one-card and two-card layouts. See [BaseOS installation guidance](/Users/pvaibhav/.t3/worktrees/BaseOS/feature-h700-mainline/README.md:63), [BaseOS 2 card selection](/Users/pvaibhav/.t3/worktrees/BaseOS/feature-h700-mainline/v2/os/overlay/etc/init.d/rcS:79), and the [upstream installation guide](https://github.com/spruceUI/spruceOS/wiki/01.-Installation-Instructions).

Both OS generations select `/mnt/SDCARD/spruce/scripts/runtime.sh` after generic, Slot, and NextUI entries and invoke it through `/bin/sh`. BaseOS 1.x explicitly creates `/mnt/SDCARD -> /mnt/sdcard` and waits for `/dev/mali0` before handoff. The repo-wide spruce search found no spruce-specific OS hardware adapter beyond this launch/path support. References: [1.x alias](/Users/pvaibhav/.t3/worktrees/BaseOS/feature-h700-mainline/overlay/etc/init.d/rcS:337), [1.x session](/Users/pvaibhav/.t3/worktrees/BaseOS/feature-h700-mainline/overlay/usr/sbin/frontend-session:162), [2.x session](/Users/pvaibhav/.t3/worktrees/BaseOS/feature-h700-mainline/v2/os/overlay/usr/sbin/frontend-session:10), and [1.x handoff tests](/Users/pvaibhav/.t3/worktrees/BaseOS/feature-h700-mainline/tests/test-frontend-session.sh:250).

Spruce runtime sources helpers, sets performance policy, repairs the card when triggered, calls `device_init`, applies Wi-Fi, starts watchdogs, and enters `principal.sh`. The latter launches PyUI or a queued game. H700 `device_init` aliases bundled Python as `MainUI`, attempts to install Bash, stages controller profiles, binds an augmented account database, and shields the legacy session path. References: [spruce/scripts/runtime.sh L11–52](https://github.com/spruceUI/spruceOS/blob/6ca7c2f393bab6ffcc390b8796d1e3ec0fa2ec0e/spruce/scripts/runtime.sh#L11-L52), [spruce/scripts/runtime.sh L101–149](https://github.com/spruceUI/spruceOS/blob/6ca7c2f393bab6ffcc390b8796d1e3ec0fa2ec0e/spruce/scripts/runtime.sh#L101-L149), [spruce/scripts/platform/h700/AnbernicXXCommon.sh L435–513](https://github.com/spruceUI/spruceOS/blob/6ca7c2f393bab6ffcc390b8796d1e3ec0fa2ec0e/spruce/scripts/platform/h700/AnbernicXXCommon.sh#L435-L513).

## Unsafe or destructive paths

These are reachable optional operations or legacy cleanup paths, not evidence that merely reading spruce source writes a device.

1. **BootLogo writes TF1's boot-resource partition.** Its H700 branch mounts `/dev/mmcblk0p2` writable and overwrites an existing `bootlogo.bmp` with `dd conv=notrunc`. It checks dimensions and byte count, which limits damage but does not make a boot-partition write safe under power loss. It also names an SD backup file. Disable this app's H700 write branch on BaseOS 2 until BaseOS offers a supported logo-update interface. Do not create its backup or leave generated BMP files on the card. ## Minimal implementation boundary

A practical first usable port needs the following coherent change set, rather than an OS shim for every vendor interface.

1. Add one BaseOS 2 capability flag in spruce before loading H700 overrides. Preserve model, settings, game, save, save-state, and credential paths. Stable's and Development's source layouts differ, so backports need the appropriate file locations.
2. Select KMSDRM SDL/Mesa in global helpers, PyUI, game launchers, and ports. Replace the PyUI startup brightness ioctl. Start with 64-bit emulators whose graphics contexts have been validated.
3. Discover evdev devices; use BaseOS volume, display, performance, sleep, Wi-Fi, Bluetooth, and power commands. Keep OS-owned services and audio configuration under BaseOS control. Consume output/lid events where needed.
4. Disable boot-logo writes, legacy OS update staging, automatic FAT repair, independent USB mass-storage export, card swap, and forced shutdown fallbacks on BaseOS 2 until each has an explicit supported integration.
5. Verify the assembled OS has the alias, Bash or a complete alternative interpreter strategy, standard utilities, loaders, and system graphics libraries. Finish missing physical-model input/rumble/LED drivers independently of spruce.

Estimated initial frontend port: roughly 1–2 developer weeks including source changes and local integration checks, before a hardware test pass. Broad emulator/PortMaster coverage, armhf GL support, and drivers for every model are separate work and can exceed that estimate. These are scope estimates, not proof that the port works.

Future qualification must check first boot and respawn, controls on every pad layout, rotated/square panels, brightness persistence, speaker/headphone/USB/BT routing, radio on/off and credential retention, lid/power/timer suspend, low battery, clean shutdown, and both card layouts. It must verify that blocked maintenance apps cannot write boot partitions or stage legacy updates. No such device tests were performed for this report.
